`<InAppMessages/>` shows the messages the current user is eligible for.
Eligibility is decided server-side: Galinum evaluates every running campaign's
targeting against the user's traits and event history, assigns an A/B variant
(stable per user, weighted), and creates a delivery record.

```tsx
<InAppMessages />
```

## One message per page view

Each page entry requests fresh, non-cacheable authority after identity and current
track facts settle. One elected renderer may commit one message. A null custom
renderer skips its candidate without exposure. Failed or timed-out entries stay
empty; a later navigation can try again. Warm content is never eligibility.

Dismissing or completing a message consumes the entry. Navigation removes an
interrupted message without sending dismissal. Queries and hashes do not create
new entries. Actual rendering reports shown; fetching alone creates no exposure.
Durable feedback and local completion survive reloads, scoped to project and user.

## Targeting screens

A campaign can name the screens it belongs on. Its `pages` patterns are matched
in the browser against the current pathname:

- A pattern starts with `/`. `*` matches any characters, including `/`.
- Everything else is literal and case-sensitive. Trailing slashes are
  normalized, and query strings and hashes are ignored.
- A campaign with no patterns is eligible everywhere.

`pages` answers **where** a message may show; the audience answers **who** sees
it. Your agent sets both through the campaigns API.

Images are warmed in the background and every message reserves its image area,
so a slow image never delays the text or shifts the layout.

## The default renderer

With no props, each message states its own presentation in
`content.presentation`:

- **`"toast"`** — a compact card fixed to the bottom-right corner, showing
  the variant's `title`, `body`, and an optional CTA button. When the message
  also carries `content.media`, the image renders as a small thumbnail
  (~48 px) inside the card.
- **`"modal"`** — a large centered announcement over a full-screen backdrop.
  With media, the image sits at the top as the visual focus, with the title,
  body, and a prominent CTA below; without media the modal renders text only.
  On desktop the modal is a constrained card (~480 px wide); on mobile it is
  near-full-width and viewport-safe. Animated GIFs animate.

Media is content, not presentation. Messages delivered by Galinum always
carry `presentation`; a cached or older payload without it falls back to the
original rule (media renders as a modal, no media as a toast).

Dismissals and CTA clicks are reported back automatically in both layouts.
CTA URLs are validated — only `http:`, `https:`, and `mailto:` schemes
render, so a compromised campaign can't inject `javascript:` URIs into your
page. Media URLs are stricter still: only `http:`/`https:` images render.

The modal follows accessible dialog conventions: it takes focus when it
opens, keeps keyboard focus inside, closes on the close button, on
<kbd>Escape</kbd>, or on a backdrop click, and returns focus to where the
user was. The image's `alt` text comes from the campaign (`media.alt`, or
empty for images marked `decorative`). If the image fails to load, the text
content and dismissal controls still render. Only one message is on screen at
a time, so a toast never sits dimmed behind a modal backdrop; when both a
modal and a toast are eligible for the same page view, the modal goes first.

All presentation is inline styles — the SDK injects no stylesheets into your
page (inherited properties like `font-family` still apply, so the cards pick
up your app's typeface).

### Theming

The built-in renderer has a light and a dark palette. The `theme` prop selects
it: `"light"`, `"dark"`, or `"auto"` (the default).

`"auto"` reads the computed `color-scheme` of your `<html>` element, the
standard way a page declares its scheme, and looks at which keywords it
contains:

- `dark` without `light` (`dark`, `only dark`) renders the dark palette.
- Both keywords (`light dark`, `dark light`) follow the user's OS preference.
- No `dark` keyword renders the light palette.

The palette also follows later changes, so your own theme toggle flips an
on-screen message live. If your app switches themes without setting
`color-scheme`, pass the value yourself:

```tsx
<InAppMessages theme={isDark ? "dark" : "light"} />
```

`theme` styles only the built-in toast and modal. A custom `render` is
unaffected.

## Custom rendering

Pass `render` to fully control the UI while Galinum keeps handling targeting,
variant assignment, and measurement:

```tsx
<InAppMessages
  render={(message, actions) => (
    <MyToast
      title={message.content.title}
      body={message.content.body}
      onCta={actions.onClick}
      onClose={actions.onDismiss}
    />
  )}
/>
```

A custom renderer follows the same schedule: it receives the one message
chosen for this page view, not a list.

`message.content` is the variant's JSON payload — the default shape is
`{ title?, body?, cta?, media?, presentation }`, but campaigns can carry any
JSON your renderer understands. The message arrives untouched
(`content.media` is `{ url, alt?, decorative? }` and
`content.presentation` is `"toast"` or `"modal"`); the layouts above apply
only to the built-in renderer, so use or ignore `presentation` as you like.

Impressions still count on render: when your `render` function returns
content for a message, the SDK reports `shown` for that delivery
automatically. Return `null` to render nothing — no impression is recorded,
and the next matching message takes its place on this page view.
Call the `actions` callbacks so Galinum can measure:

| Action | Meaning |
| --- | --- |
| `actions.onClick()` | the user engaged with the CTA |
| `actions.onDismiss()` | the user closed the message |
| `actions.onConvert()` | the user completed the campaign's goal |

## Reporting conversions elsewhere

If conversion happens outside the message UI (e.g. on a later page), report it
with the hook:

```tsx
const { sendFeedback } = useGalinum();
await sendFeedback(deliveryId, "converted");
```


## Fresh entries and shared completion

Every navigation creates an entry before its no-store decision request. The
server echoes userId, entryId and requestId. The SDK rejects prior-entry,
prior-identity and outdated-facts responses. A failed or ten-second-deadline entry
settles empty; a later navigation can try again. Cached eligibility never displays.

Web and native use the same project/user/campaign delivery and stable variant.
Completion acknowledged before another client's later entry suppresses it there.
There is no global display lease. Remote completion concurrent with an authorized
entry can race its paint. Known local facts mutations invalidate uncommitted
authority immediately, including a settled candidate awaiting its renderer.
Already-painted messages are not globally retracted.

Feedback is durable per captured project/feedbackId, with immutable user/delivery/type. Terminal feedback
requires a durably admitted same-entry shown predecessor and waits for its
validated acknowledgement. Missing or rejected predecessors produce failed
admission; the built-in renderer stays available for retry. sendFeedback returns queued, acknowledged,
rejected or failed admission. flushFeedback processes a bounded page; retrying
the same delivery/type reads its status. A replay never creates a new billing
exposure in another period; a distinct committed render has its own stable ID. Browser storage failures are explicit.

CTA destinations are typed: {label,destination:{kind:"website",url:"https://app.example.com/exports"}}.
For app URLs, use kind:"app" and configure appSchemes on GalinumProvider.
No mandatory website-origin allowlist is required.


## In-app receipt upgrade

Existing databases require the separate transactional
packages/server/upgrades/inapp.sql after the installation and push upgrades.
Back up and stop API workers, apply it with psql -X -v ON_ERROR_STOP=1 -f,
then update SDK callers together with the server. Fresh schema initialization
already includes the receipt table. Each actual shown operation has a stable
feedbackId; retries preserve it, while distinct committed renders get new IDs.
Receipt storage is indexed per operation, without a lifetime replay cap.


Feedback acknowledgement requires a canonical HTTP 200 receipt with the captured
user, delivery, type and feedback ID, and a valid integer first timestamp.
Malformed or mismatched success bodies are retryable, never permanent success.
Identify invalidates facts at invocation and settlement; uncommitted entry
authority cannot outlive a known mutation.
