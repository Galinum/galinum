---
title: "GitHub integration"
description: "Prepare communications from code changes, review drafts, and launch when your product is ready."
---

Connect a repository so Galinum can prepare communications from relevant code
changes. Pushes to your selected branch cover both direct commits and merged
pull requests. In Galinum Cloud, approved communications can launch when
GitHub reports a successful production deployment within your confirmed scope.

## Connect a repository

1. Select your project in Galinum.
2. Open **Settings → GitHub** and connect your GitHub account.
3. Install the Galinum GitHub App for the repositories you want it to read.
4. Select a repository and its target branch, usually `main`.
5. Add project instructions for the agent's audience, tone, and announcement priorities.

The App reads repository contents, pull requests, and deployment evidence. It does not write code,
comment on PRs, or block merges and deployments.

Galinum starts from the branch's current state when you connect it. Later
pushes become new input. It does not announce the repository's full history.

## Prepare drafts before a PR merges

Enable **Draft from ready pull requests** to prepare communications earlier.
A non-draft PR targeting your selected branch becomes eligible when it opens
or is marked ready for review. Opening a draft PR alone does not start drafting.

Relevant commits refresh the existing draft. Returning the PR to draft pauses
updates for that PR. Closing it without merging withdraws its contribution.
Merging reconciles the early draft with the branch change instead of creating
a duplicate campaign.

## Review a communication

The agent assesses customer impact using the code changes, repository context,
project instructions, and existing campaigns. It groups related changes into
an unlaunched campaign. Unrelated changes can produce separate drafts. Changes
without communication value produce no campaign. You do not need a PR label
or checkbox.

Open the campaign to inspect its current content and GitHub sources. Approval
records your review. In automatic mode, approval can make the campaign eligible
to launch immediately if its changes are still deployed. Deployment success
never replaces approval.

## Revise with your own agent

Copy the revision prompt from the campaign and add your feedback. Run it in
an agent connected to the authenticated [Galinum MCP server](/mcp-server).
The prompt identifies the actual campaign, so the revision appears in the
same dashboard preview.

Relevant GitHub changes can still update a customer-edited draft. The agent
uses its current content and preserves unrelated edits. Approval survives
these revisions. Refresh the preview to inspect the latest content.

## Configure deployment tracking

In **Settings → GitHub**, select a repository, its exact production environment,
and the sources that this deployment ships. Describe the deployment scope and
explicitly confirm it. A human manager must make this configuration. An agent
cannot infer the scope or confirm it for you. One repository does not necessarily
represent one deployed application.

Projects initially use **automatic** launch. You can change the project default
or set an individual campaign to **automatic** or **manual**. Selecting the
project default clears the override to `null`. Default changes affect every
unlaunched campaign without an explicit override; explicit overrides stay unchanged.

Saving deployment tracking also evaluates existing approved drafts. Eligible
automatic drafts can launch without another approval or deployment. Select
manual mode before setup for communications you want to launch yourself.

## Automatic launch

Automatic launch requires approval and current deployment coverage for every
associated change across **all** required repository/environment mappings.
A missing or unclear mapping prevents automatic launch. Drafting and grouping
remain available when mapping is unclear.

If deployment succeeds before approval, later approval makes the communication
eligible while its changes remain deployed. Source revisions retain approval.
Automatic launch uses the latest content and checks its current associated
changes, rather than the changes present when you approved it.

Project and source pause controls, withdrawn or unresolved sources, launch
readiness, and delivery expiry still apply. A future `deliverFrom` permits
activation but delays delivery until that window opens. An expired
`deliverUntil` blocks activation.

The campaign's activation panel shows the effective mode, approval, waiting
reasons, coverage for each mapping, last check, launch evidence, and warnings.
The [management API](/api/overview) exposes this state through
`GET /api/v1/campaigns/{id}/activation` and the default through
`GET /api/v1/launch-policy`. Revision-checked PATCH requests change these modes;
they do not approve campaigns or configure deployment scope.

## Launch manually

Use **manual** mode for feature flags, gradual rollouts, and unclear deployment
mappings. Select **Launch** when the intended audience has access. Manual launch
uses the existing readiness and lifecycle checks without requiring GitHub
deployment coverage. No deployment integration is required for manual launch.

## Deployment evidence and retries

Only successful deployments in the configured repository and exact environment
can establish new coverage. Pending, failed, and unselected-environment deployments
cannot. A newer failed or pending deployment does not erase previously deployed
code. A later invalidating status on the selected deployment leaves evidence
unknown; Galinum does not fall back to a superseded success.

GitHub reports deployment status; it does not independently inspect your running
application. Galinum checks direct commit ancestry and complete merged PR bundles,
including merge, squash, and rebase results. All required changes must be covered.
Git history alone does not prove that a feature is available to its audience.

Evidence reads have bounded page, request, and byte limits. Missing history,
ambiguous source identity, incomplete comparisons, stale provider responses, and
provider failures leave evidence unresolved. They never count as successful
coverage or proof of rollback. Periodic reconciliation retries pending work,
including missed signals and temporary failures. Duplicate, delayed, out-of-order,
and concurrent signals do not duplicate initial launch or restore stale evidence.
Already started, paused, or ended campaigns never restart from replayed signals.

## Rollbacks and reverts

An explicit rollback that excludes required changes, or a deployed identifiable
revert, invalidates coverage for an unlaunched communication. Detection uses
Git/deployment evidence and canonical full-SHA revert declarations. A causal
revert of a revert can restore coverage; unrelated reverts do not cancel each
other. Ambiguous or incomplete history remains unknown. Galinum does not ask an
agent to infer feature removal from arbitrary code edits.

If the communication already launched, including a manual launch, deterministic
coverage loss creates a warning on the communication and in the dashboard agent
activity feed. Warnings identify the affected changes and deployment evidence.
They do not automatically pause delivery, change its window, or send email.
You decide whether to pause the communication. Later relevant source changes
can still produce another unlaunched draft.
